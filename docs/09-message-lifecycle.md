# 09 — Message Lifecycle

Cue's private messages are **ephemeral by default**. Keeping one is a deliberate, mutual,
visible act. This is the Snapchat model applied to a security tool, and it is the single
biggest UX departure from Signal.

## The default: deliver and delete

```
send ──► Node holds ciphertext ──► delivered to every device ──► Node DELETEs
                                            │
                                            ▼
                              client holds it for the conversation's
                              retention window, then destroys it
```

**Server side:** an envelope exists only until every recipient device acknowledges it.
Undelivered envelopes expire at 30 days. There is no archive, no backup of the queue, and
no copy that survives delivery. A seized Node yields in-flight ciphertext for people who
happened to be offline, and nothing else.

**Client side:** each conversation has a retention window, visible in the header:

| Window | Default for |
|---|---|
| On read + 1 minute | — (opt-in, the strictest) |
| 24 hours | — |
| 7 days | **DMs and groups (default)** |
| 30 days | — |
| Keep until I delete | — (opt-in) |

Either participant can propose a change; it applies to messages sent *after* the change,
and both sides see an in-thread event: *"candid-harbor019 set messages to disappear after
24 hours."* Nobody's retention setting can silently shorten or lengthen what the other
person already has.

## Mutual save

The exception, and the only way a private message outlives its window:

1. Anyone in the conversation taps **Save** on a message. It's marked *"Save requested"*
   and everyone in the conversation sees it, in place, immediately.
2. The other participant (or, in a group, **every** participant) confirms.
3. The message is pinned: exempt from expiry, marked with a save indicator and who saved
   it, and listed in the conversation's **Saved** view.
4. Any participant can **unsave** at any time. Unsaving returns the message to the normal
   retention rules, which usually means it is destroyed at once on every device. This is
   deliberate: consent to retention is continuously revocable, not a one-time grant.

Design notes:
- **Groups require unanimity.** In a 20-person group that's friction, and that's the point
  — a message kept forever is a message any of 20 people can be compelled to produce.
  Groups can enable "majority save" in settings; it is off by default and shown in the
  group's info panel.
- Saved messages live in the local encrypted DB on each participant's devices. **Nothing
  about a save is stored on the Node** — save state is an E2EE control message between
  participants like any other, so the Node cannot tell a saved conversation from a
  disappearing one.
- Attachments follow their message. Saving a message saves its attachment; unsaving
  destroys the local blob.
- A newly linked device does not receive saved history from the Node (there's nothing to
  receive). It can pull it from another of the user's devices over an encrypted local
  transfer, if the user chooses.

## Screenshots and the honest limit

Cue does **not** implement screenshot detection as a security feature. It is unreliable
(a second phone, a VM, a camera), it is trivially bypassed, and — the real objection — it
teaches users to feel protected when they are not, which gets people hurt.

The app states this once, in plain language, during onboarding: *"Anyone you message can
keep a copy of what you send. Disappearing messages protect you from devices being seized
later — not from the person you're talking to."*

That sentence is the entire honest security model of ephemerality, and it belongs in front
of users rather than in a FAQ.

## Message features

| Feature | Behaviour |
|---|---|
| Edit | Allowed for 15 minutes; edit history not retained; recipients see an "edited" marker |
| Delete for me | Local only |
| Delete for everyone | Sends a tombstone; honoured by honest clients, cannot be enforced against a modified one. UI says "requested", not "deleted" |
| Reactions | E2EE control messages, padded like any message |
| Replies / quotes | Quoted content is included in the reply's ciphertext, so a reply survives the original's expiry |
| Typing indicators | On by default in DMs, off in Quiet Mode, per-conversation toggle |
| Read receipts | Same |
| Forwarding | Marked as forwarded with a hop count, like Signal/WhatsApp, to slow viral misinformation. Saved-message state does not transfer |
| Voice notes | Attachment path, waveform generated client-side |
| Link previews | **Generated by the sender**, sent inside the ciphertext. The receiving client never fetches a URL. Non-negotiable: auto-fetching a link on receipt is a deanonymisation attack |
| Formatting | Markdown subset, rendered through an allow-list sanitiser, no raw HTML |
| Disappearing-message timers | Per conversation, as above |

## Attachments

- Encrypted client-side with a per-blob random key; the key travels in the message.
- Uploaded under an anonymous upload token to the Node's blob store; the Node sees a
  ciphertext blob and a size bucket.
- Downloaded after a small randomised delay to decorrelate upload from download.
- **All metadata is stripped client-side before encryption** — EXIF GPS, camera serial,
  timestamps, document authorship. Done in the core, not the UI, so every client gets it.
  Users are shown what was stripped on first use.
- Size buckets, like messages, so an observer sees a bucket rather than an exact size.
- Blobs are garbage-collected when their message expires, and at a 30-day hard TTL.

## Delivery semantics

- At-least-once delivery; client-side dedup by envelope ID.
- Ordering is per sender-device pair. There is no global conversation ordering, because
  establishing one requires the Node to know more than it should. Clients order by a
  logical clock plus sender-supplied timestamp and tolerate small reorderings.
- Sender-side queue: messages composed offline are held locally, encrypted, and sent on
  reconnect. The queue survives restarts and respects cover-traffic scheduling.
- Failed delivery after the 30-day TTL surfaces as "not delivered" in the sender's UI.

## Notifications

- Desktop notifications carry **no content by default** — "New message" only, with a
  per-conversation opt-in to show sender and preview.
- Notification content is rendered from the locally decrypted message; nothing is ever sent
  through a third-party push service in the desktop client, which maintains its own socket.
- Mobile (post-1.0) is where this becomes genuinely hard: APNs and FCM mean a third party
  learns that a message arrived, and when. The intended answer is a content-free push
  wake-up with randomised delay and batching, plus UnifiedPush for Android users who want
  no Google involvement. Flagged in `docs/12` because it is a real unsolved cost of the
  mobile plan.
